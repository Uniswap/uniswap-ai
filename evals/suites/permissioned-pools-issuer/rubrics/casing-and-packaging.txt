# Casing and Packaging Rubric

Evaluate whether the response gets the permissioned-pools identifiers, the checker's required
shape, and the dependency-install story right.

Only score elements the question actually raises. If the question is about installing the
contracts, score elements 4 and 5 and treat 1 to 3 as not applicable; if it is about writing a
checker, score elements 1 to 3 and treat 4 and 5 as not applicable. Divide by the number of
applicable elements.

## Required Elements

1. **Exact identifier casing**
   - The contract to extend is named `BaseAllowlistChecker` (lowercase "l" in "list").
   - The file it lives in is `BaseAllowListChecker.sol` (capital "L").
   - The response explains that the file name and the contract name differ, and shows the Foundry
     `path:Contract` form or an import path that reflects it.
   - The function is `checkAllowlist(address account, address tokenAddress)` returning
     `PermissionFlag` (singular type; `PermissionFlags` is the library).

2. **The visibility pair**
   - If extending the base contract: `public view virtual override` (or `public view override` /
     `public view virtual`) — because the base declares the function `public virtual`.
   - If implementing `IAllowlistChecker` directly: `external view` is correct.
   - Credit an answer that explains why the two differ, or that notes a `public virtual` function
     cannot be overridden with `external`. An answer that gives only the shape matching the route
     the question asked for is still correct.

3. **The ERC-165 precondition**
   - The adapter's constructor checks that the checker advertises `IAllowlistChecker` through
     ERC-165, and reverts `InvalidAllowListChecker` if it does not — so
     `createPermissionsAdapter` fails at that point, not later.
   - Extending the base contract supplies `supportsInterface` already; implementing the interface
     directly means writing `supportsInterface` yourself.

4. **The install path**
   - Foundry with the commit pinned:
     `forge install Uniswap/v4-periphery@3245c3cb99c48fa1dc2459c3b60abc37d4294aba`.
   - The `@uniswap/v4-periphery/=lib/v4-periphery/` remapping, so the guide's npm-scoped import
     paths resolve.
   - States that the npm package is not a viable install path for these contracts, because the
     published releases do not contain `src/hooks/permissionedPools/`.

5. **Why a commit and not a version**
   - `v4-periphery` has no git tags, so a raw commit SHA is the only way to pin.
   - Does not invent a version number, a tag, or a release date.

## Penalize

- Any emitted Solidity that inherits from, or imports a contract named, `BaseAllowListChecker`
  (capital "L" as the *contract* name). Quoting the capital-L spelling while explaining that it is
  the file name is correct and must not be penalized.
- Any claim that the published deploy guide extends `BaseAllowlistChecker`. The guide implements
  `IAllowlistChecker` and `ERC165` directly and never mentions the base contract. Both routes
  compile; misattributing the guide's route is the error.
- Recommending the npm package as the install path, or presenting a version number as containing
  these contracts.
- A commit SHA that differs from the one above, or a fabricated tag.
- Emitting a deployment address as canonical.

## Scoring Guide

Score the fraction of applicable elements that are correct and complete, then subtract for each
penalized item:

- All applicable elements correct: 1.0
- One element materially incomplete: 0.85
- One element wrong or two incomplete: 0.7
- Two elements wrong: 0.5
- Most elements wrong: 0.2 or below
- Subtract 0.2 for each penalized item present.
