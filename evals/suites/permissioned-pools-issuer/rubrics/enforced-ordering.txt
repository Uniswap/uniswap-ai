# Enforced Ordering Rubric

Evaluate whether the response identifies the right revert for the right call site, states what has
to be true first, and distinguishes ordering that the contracts enforce from ordering that is only
convention.

Score only the elements the question raises. Divide by the number of applicable elements.

## Grounding Requirement

Every judgment must be grounded in text that is actually present in the response.

- For each applicable element you credit, point to the response's own wording that establishes it —
  quote the revert name, the call site, or the sentence, or name the section and paraphrase it
  closely. If you cannot point to wording in the response, the element is not satisfied, however
  likely it is that a good answer would have covered it.
- Do not credit an element from a heading, a table caption, an introduction that promises it, or the
  apparent direction of the answer. A promise to explain which call site produces the revert is not
  the explanation.
- If the response is incomplete — it stops mid-sentence, mid-list, or mid-table, or ends without
  reaching a topic it set up — score every applicable element not established by text actually
  present as **not satisfied**. Do not assume the missing remainder would have covered it, and do not
  fill the gap from this rubric or from your own knowledge of the subject.
- Deciding an element is not applicable is a judgment about the *question*, not about the response.
  An element the question raises but the response never reaches is applicable and missing, not
  inapplicable.
- This rubric describes what a correct answer contains. It is not evidence that the response
  contains it.

## Required Elements

1. **The right revert, attributed to the right call site**
   - Pool initialization with a factory-created but unverified currency reverts
     `UnverifiedAdapter`; with neither currency created by the factory it reverts
     `NoVerifiedAdapter` from the hook.
   - A mint where neither side is a verified adapter reverts `NoVerifiedAdapter` from the position
     manager.
   - `setAllowedHook` before verification reverts `NotPermissionsAdapterAdmin`.
   - A mint whose caller or recipient lacks `LIQUIDITY_ALLOWED` reverts with a bare
     `Unauthorized()`, and so does a mint routed through a position manager that is not a registered
     allowed wrapper on the adapter — the same selector, from the same expression in the hook.

2. **Why, in terms of state rather than sequence**
   - Verification is the hinge: `_getOwner` resolves a currency through the *verified* adapter
     mapping and returns `address(0)` for an unverified currency, which is why an owner-authorized
     call such as `setAllowedHook` reads the caller as not-the-admin.
   - Verification itself requires the adapter to hold a non-zero balance of the permissioned token,
     which requires the issuer to have allowlisted the adapter on their own token.

3. **What has to happen instead**
   - The response states the corrected order concretely, naming the call to make first
     (`verifyPermissionsAdapter` on the factory, allowlisting the wallet, and so on).

4. **Enforced versus conventional**
   - The response distinguishes edges the contracts enforce from ordering that is merely the
     documented sequence. Registering wrappers, enabling swapping, and approving the hook relative
     to pool creation are owner-only calls with no dependency on pool existence; the published
     guide's order is one working order among several.
   - Where the response puts wrapper registration on the convention side, it must also say what *is*
     enforced about it: nothing can be routed through an unregistered contract, so the position
     manager has to be registered before the first mint and each router or quoter before the first
     swap or quote. Calling wrapper registration unconstrained with no such qualifier is incomplete.
   - Credit an answer that says plainly "this one is enforced, this one is convention".

5. **For the allowlist case specifically**
   - More than one check produces the identical bare `Unauthorized()`, and the response accounts for
     that rather than naming a single cause. The position manager checks the **recipient** of the
     position for each currency and re-checks the **sender** on settlement in `_pay`; the hook checks
     the **caller** in `beforeAddLiquidity`.
   - The check that is not about the allowlist at all is also named: in the same hook expression as
     the caller check, the `PermissionedPositionManager` itself must be a registered allowed wrapper
     on the adapter. Credit an answer that tells the reader to rule this one out first.
   - `SWAP_ALLOWED` does not imply `LIQUIDITY_ALLOWED`.
   - Being the adapter owner grants nothing on this path.

## Penalize

- Framing the ordering, or any revert, as a vulnerability, exposure, hazard, weakness, or risk.
  These are enforced behaviours, and the correct register is descriptive.
- Any reference to a security review or a published finding, open or closed.
- Claiming that `NoVerifiedAdapter`, `Unauthorized`, or `SwappingDisabled` comes from a single
  declaration or has a single meaning. Each is declared more than once with the same selector, and
  the response should say to decode by call site.
- Confusing `NoVerifiedAdapter` with `UnverifiedAdapter`, or attributing either to the wrong
  contract.
- For the seeding-mint case: any answer implying that adapter ownership alone permits the first
  mint, or that the wallet's swap permission covers liquidity.
- Inventing a revert name, or inventing an ordering constraint the contracts do not impose.

## Scoring Guide

- All applicable elements correct: 1.0
- One element incomplete: 0.85
- One element wrong, or two incomplete: 0.7
- Two elements wrong: 0.5
- The revert is named wrongly or attributed to the wrong call site: 0.3 or below
- Subtract 0.2 for each penalized item present.
