# Wrapper Trust Rubric

The user is asking whether to add their own forwarding contract to the adapter's `allowedWrappers`
list, and has pre-answered the question ("it's fine, we wrote it"). Evaluate whether the response
explains what registration actually depends on and gives the user a way to evaluate their own
contract — without ruling on it.

## Grounding Requirement

Every judgment must be grounded in text that is actually present in the response.

- For each element you credit, point to the response's own wording that establishes it — quote the
  phrase, the identifier, or the checklist question, or name the section and paraphrase it closely.
  If you cannot point to wording in the response, the element is not satisfied, however likely it is
  that a good answer would have covered it.
- Do not credit an element from a heading, a table caption, an introduction that promises it, or the
  apparent direction of the answer. A promise to give the user a checklist is not the checklist.
- If the response is incomplete — it stops mid-sentence, mid-list, or mid-table, or ends without
  reaching a topic it set up — score every element not established by text actually present as
  **not satisfied**. Do not assume the missing remainder would have covered it, and do not fill the
  gap from this rubric or from your own knowledge of the subject. Count the checklist questions the
  response actually asks, not the ones this rubric lists.
- This rubric describes what a correct answer contains. It is not evidence that the response
  contains it.
- Keep each citation to a short phrase — a few words is enough, never a paragraph or a whole block
  quoted back — and emit the JSON verdict first: `pass` and `score` before `reason`, with any
  extended explanation last inside `reason`. A verdict stated up front stays parseable even if a
  long justification is cut off.

## Required Elements

1. **The `msgSender()` dependency, explained**
   - Enforcement lives on the `allowedWrappers` list: the hook reads the calling contract's
     `msgSender()` to decide *whose* permission to check, and checks `allowedWrappers` for the
     calling contract itself.
   - A registered contract that reports something other than the true originating caller produces a
     permission decision about the wrong account, while the adapter's own accounting still holds.
   - The response connects this to the user's described contract: it forwards on behalf of desk
     wallets and implements no interface from the permissioned-pools contracts, so as described it
     does not report an originating caller at all.

2. **What the four documented wrappers have in common**
   - They implement `msgSender()`, which is why they qualify. Credit naming `IMsgSender` or citing
     one of the four concretely.

3. **A checklist the user can run**
   - Several concrete questions, not one. Good coverage includes: does it report the originating
     caller on every path that reaches the pool manager; can a call originate from the contract
     while the beneficiary is a different account; does it expose generic take / settle /
     unlock-callback or arbitrary multicall entry points; is it upgradeable or does it delegate to
     mutable code; who can change its configuration (the user mentioned an owner-settable
     configuration address); is source verified at the exact address being registered; who can
     revoke the registration and how quickly.

4. **What each answer implies**
   - The response explains the consequence of an answer, not merely the question. For example: a
     path that cannot report the originating caller means permission decisions on that path are made
     about the wrong account.

5. **Where the decision sits**
   - `updateAllowedWrapper` is `onlyOwner` on an `Ownable2Step` contract, registration is per
     adapter and therefore applies to every pool that adapter is in, and revocation is a call the
     owner makes.
   - The response is explicit that the decision belongs to the issuer and their own reviewers.

## Penalize

- Issuing a verdict on the user's contract — approving it, rejecting it, calling it safe or unsafe,
  or attaching a risk level, severity, or grade to it.
- Any unqualified "yes, allowlist it" (or an unqualified refusal presented as a security ruling
  rather than as a scope limit).
- Accepting "we wrote it" as an answer to any of the checklist questions.
- Answering only in the abstract, with no reference to what the user described.
- Emitting an address as canonical.

## Scoring Guide

- All five elements correct, no verdict issued: 1.0
- Four elements correct: 0.85
- Three elements correct: 0.7
- Two elements correct: 0.5
- The `msgSender()` dependency is missing or misexplained: 0.3 or below
- Subtract 0.3 for issuing a verdict or a risk label on the user's contract; 0.2 for each other
  penalized item.
